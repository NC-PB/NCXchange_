# Phases

The build order of `../architecture/architecture.md` (section 12, milestones M1 to M10) grouped into phases, each with what it delivers, what it needs, and the condition that closes it. Every phase ends with a runnable `ncx` command and green tests, so the project can be shown at any point. The tasks of each phase are in `tasks/inbox/`, named `P<phase>-<nn>-<slug>.md`; a task moves to `tasks/done/` when its acceptance criteria hold on the main branch.

| Phase | Milestones | Delivers | Closed when |
|---|---|---|---|
| 0 Foundations | M1 | the repository, the solution with the `Ncx.*` projects, analyzers and settings from the code guidelines, `Ncx.Core` with the word catalog, lexer, parser, expressions and the canonical writer, `ncx format`, the folder READMEs and `reading-the-code.md` | the five `.ncx` examples parse and format to themselves byte for byte; the analyzers are quiet; the CI runs the tests on every push |
| 1 Virtual machine | M2 | state classes, block execution (motion, arcs, cycles, tool change, frames, `JUMP`/`REPEAT` recording and `CALL` following per D99), validation with every ERROR and WARNING of the list, events with Before and After, the expander with `@SAVE`/`@RESTORE`, `ncx check`, `ncx trace`, `ncx annotate` | the examples check clean (no ERROR without a machine file, D103); every validation rule has a test; the coolant clutch rule expands and restores; trace and annotate output exists for `2.5D_FRAESEN.ncx` |
| 2 Machine configuration | M3 | `Ncx.Config`: TOML loading with Tomlyn into the typed records of `Ncx.Core` (D107), templates rendered and matched both ways, roles and resources, axes and limits, the cycle catalogs, the job manifest and vars files, `millturn1.toml` as a fifth example machine (D104) | the five example machine files load; the five examples check with no ERROR with their machine files; a template renders from an NCX block and matches back to the same words; a bad file reports the line |
| 3 Readers and compilers, first pair | M4, M5, M6 | `Ncx.Readers` with the Fanuc and Heidenhain readers and their source-side state; `Ncx.Compilers` with the Heidenhain and Fanuc compilers and the number formatting; `ncx convert`, `ncx compile` | `2.5D_FRAESEN` reads from both sources to the same canonical text and compiles back to both without loss; `BOHREN` and `3D_FRAESEN` round-trip; the corpus programs of both families never crash the readers |
| 4 Interpreted VM and analytics | M7 | expression evaluation, jumps and calls, block cap, `Ncx.Analytics` with the tool list, runtime estimate, segment length and tool vector change, `ncx analyze` with `--from`/`--to` | `PATTERN_LOOP.ncx` runs to the end with the expected variable values; the analytics run on `3D_FRAESEN` and on a 5-axis program and their results are recorded as the reference |
| 5 Siemens | M8 | the SINUMERIK 840D sl reader and compiler: units and archives, `=` addresses, frames with the replacing and additive semantics, `T=`, `M6`, `D`, `SETMS`, cycles with the sl signatures, `PROC`/`RET`, `WAITM` | `MILLTURN_TRANSFER.ncx` compiles for `millturn1.toml` (generic words only, D104); the Hermle C22 U and a Burkhardt+Weber program of the corpus read without loss and compile back |
| 6 Jobs and channels | M9 | the round-based scheduler, the job manifest, channel binding in the job compiler, `SYNC` with marks and path forms | the two Nakamura WY250L programs read as a job, analyze without deadlock and compile back with their wait codes |
| 7 Plugins and release 1.0 | M10 | `Ncx.Plugins` with the loader behind the four interfaces (the interfaces live with their callers, D106), assembly loading in a context per plugin that shares the `Ncx.*` assemblies with the host (D106), the plugin template, `ncx plugin new/build/check/test`, `docs/plugins.md`, packaging of the `ncx` tool, the release checklist | the template builds and runs unchanged; the coolant clutch sample expands and restores through a plugin; a sample plugin puts Z on its own line; a tagged 1.0 with release notes |
| later | | the kinematics module (tool pose from the `[[node]]` tree, vector-to-axis conversion, `TILT` to `TILT_AXIS`), further controllers (Mazak EIA specifics, Okuma OSP), Heidenhain turning, GILDEMEISTER structure programming, a GUI or web front end | out of scope for 1.0 |

Order inside a phase: the task files carry `Depends on`; tasks without a dependency on each other may run in parallel. Across phases the order is the table order, with one change: P2-01 and P2-02 (configuration loading and templates) are done between phase 0 and phase 1, because the virtual machine reads the configuration from its first task (roles, axes, tolerance, reference points), and P2-03 and P2-04 follow phase 1; the phase 1 row "the examples check clean" means no ERROR without a machine file (D103), the phase 2 row adds no ERROR with their machine files.

Working rules, from `../architecture/code-guidelines.md`: every change cites the specification sentence it implements, the tests are string in and expected text or state out, the example files are the acceptance tests, a decision that had to be taken gets a row in `../decisions/decisions.md`, and from phase 1 on the definition of done (section 12 there) applies in full.
