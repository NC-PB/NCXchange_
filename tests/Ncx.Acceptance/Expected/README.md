# Expected outputs

What the acceptance tests expect, one file per example and output, compared as a whole file (code-guidelines 8): `<name>.check.txt` is the list of diagnostics of a STATIC check of the example without a machine file, one line each in the form of D98 (`../Examples/ExampleCheckTests`, P1-04, and `ncx check` in `../Cli/CheckCommandTests`, P1-07). `<name>.<machine>.check.txt` is the check of the example against a shipped machine file found by name, the three mill examples with `heidenhain-itnc530` and `fanuc-mill-30i`, `MILLTURN_TRANSFER` with `millturn1`, `POLAR_FACE` with `nakamura-ntjx` (`../Examples/ExampleMachineCheckTests`, P2-04). An empty file is a check without a diagnostic. `2.5D_FRAESEN.events.txt` is the event sequence of that example (`../Examples/ExampleEventTests`, P1-05); `2.5D_FRAESEN.trace.txt` and `2.5D_FRAESEN.annotate.txt` are what `ncx trace` and `ncx annotate` write for it without a machine file (`../Cli/TraceCommandTests`, `../Cli/AnnotateCommandTests`, P1-07). `PATTERN_LOOP.trace-interpreted.txt` and `INCREMENTAL_SUB.trace-interpreted.txt` are what `ncx trace --interpreted` writes for the two examples with a flow: the five passes of the loop with Q1 and Q3, the four calls of the subprogram (`../Cli/TraceInterpretedTests`, P4-01).

`analytics/` holds the reports of `ncx analyze` that are the reference of the analytics for later versions (implementation 14, P4-02 and P4-03), compared by `../Analytics/AnalyticsReference` in `../Cli/AnalyzeCommandTests` and `../Analytics/SegmentAndVectorReferenceTests`:

- `analytics/2.5D_FRAESEN.tools.txt`: the tool list of the example without a machine file, one row, tool 1, whose distances `../Analytics/ToolListAnalyticTests` computes by hand from the example.
- `analytics/3D_FRAESEN.fanuc-mill-30i.runtime.txt`: the runtime estimate of `docs/spec/examples/sources/3D_FRAESEN.fanuc.nc`, converted with `fanuc-mill-30i` and analyzed on it: 191.5 s. Unverified: the maintainer's measured cycle time of the part is not known yet, and the dynamics of `machines/fanuc-mill-30i.toml` are plausible values, not verified on a machine (D100). When the measured time is known, the estimate must lie within 10 percent of it (P4-02), and the machine file is corrected rather than the code where it does not.
- `analytics/3D_FRAESEN.fanuc-mill-30i.segments.txt` and `.vectors.txt`, `analytics/3D_FRAESEN.heidenhain-itnc530.segments.txt` and `.vectors.txt`: the segment length and the tool vector change of `3D_FRAESEN` from each of its sources, converted with the machine file of its controller and analyzed on it (P4-03, M7). Both give the same lengths: 816 motions of known length from 0.024 mm to 131.56 mm, mean 21.397 mm, checked against an independent computation from the NCX text when they were frozen; the line numbers of the ten shortest differ by the two `RAW` lines of the Klartext header. The four skipped motions are the two that start from the reference point of the MACHINE frame (D100) and the two that end the program in the machine frame. The mills have no rotary axis, so every tool vector is the normal of the `WORKPLANE` and changes by 0.
- The 5-axis A/C pair of the maintainer's corpus gets `analytics/<part>.heidenhain.segments.txt`, `.vectors.txt` and the `fanuc` ones once `NCX_CORPUS` holds it in its folder `5X` with its machine files (`../Analytics/FiveAxisCorpusFactAttribute`); until then its test is skipped with a message, and a first run writes its reports to the temporary folder for review.

The NCX files that no document holds and a reader produces are frozen here after a review against the specification, so that a change in the output of a reader shows as a diff.

- `BOHREN.ncx`: `docs/spec/examples/sources/BOHREN.fanuc.nc` read by the Fanuc reader with `machines/fanuc-mill-30i.toml` (phase 3, P3-02), reviewed against `controller-mapping.md` 5 before it was frozen: `G81`, `G73`, `G83`, `G84` and `G85` are `CYCLE=DRILL`, `CHIP_BREAK`, `PECK`, `TAP` and `REAM`; `R` and `Z` the absolute `CLEARANCE` and `DEPTH`; `SURFACE=0` (R minus a clearance the machine file does not name, or 0); `G99` is `CYCLE_RETRACT=CLEARANCE`; the `F` of the control is `CYCLE_F`, also on `G73` and `G83`, which write no `F` of their own; `P` is `CYCLE_DWELL` in seconds; the pitch of `G84` is `F / S`; the defining block calls at its own position with a bare `CYCLE_CALL`, every position block after it with `CYCLE_CALL X=`; `G80` is `CYCLE=OFF`. The Heidenhain reader (P3-05) is compared with the same file, block for block, except the blocks the two sources write otherwise, which `../Examples/HeidenhainReaderTests.cs` lists with the rule or the open question behind each (the file keeps the Fanuc reading of `G99` and `R5.` until the question of `SAFE` against `Q204=5` is answered). It is read by `../Examples/FanucReaderTests.cs` through the repository root, never through the working directory (`../../README.md`).

On a difference the test writes what it got to the temporary folder `ncx-acceptance`, so that the two files can be compared with a diff. A change here is a change of what the examples report, and it needs the rule or the decision that explains it.
